## 18.2 Ключевые требования

| Требование | Значение |
|---|---|
| Тик симуляции | 0.5 игровых секунды, фиксированный `[СБ]` |
| Тиков на обновление | slow 1 / normal 1 / fast 16 / ultrafast 48, максимум 1000 `[СБ]` |
| Игровых секунд в реальную секунду | 1 / 25 / 250 / 500 `[СБ]` |
| Пересчёт маршрутов при изменении сети | ≤ 200 мс (до 500 станций и 1000 линий) `[Р]` |
| Полный суточный расчёт | ≤ 4 с `[Р]` |
| Перезагрузка крупного города | ≤ 8 с `[Р]` |
| Память | куча V8 = (RAM − 2 ГБ), минимум 2 ГБ; переопределение игроком, минимум 1 ГБ `[СБ]` |
| Размер сохранения | сжатый; ориентир < 50 МБ для крупной сети `[Р]` |
| Оффлайн | обязательно; карта города скачивается один раз `[СБ]` |

## 18.2а Модель данных рантайма `[ТР]`

Шесть словарей — копируем дословно из эталонной реализации (§8.6.1). Дополнительно фиксируем инварианты, которые код подразумевает, но не проверяет:

| Инвариант | Проверка при загрузке | При нарушении |
|---|---|---|
| `stoptimes_dict[route]` отсортирован по отправлению | assert на первые 3 трипа | пересортировать + warning |
| `footpath_dict` транзитивно замкнут | `check_footpath` `[ТР]` | достроить замыкание |
| FIFO: никакой рейс не обгоняет предыдущий | попарное сравнение соседних трипов | удалить ранний рейс (`remove_overlapping_trips` `[ТР]`) |
| Нет solo-routes без пересечений | пересечение множеств остановок | удалить с warning |
| Нет круговых дублей `(trip, stop)` | `drop_duplicates` | удалить дубли |
| `departure_time` может равняться `arrival_time` | — | dwell подставляется отдельно (не ноль) |

**Язык реализации `[Р]`:** горячий цикл (раунды, сканы, метки) — на типизированных массивах, **время — int секунды**, без объектов даты. Загрузка и построение словарей — на любом языке. Это прямо следует из анализа `[ТР]`: pandas-объекты в горячем цикле — главный тормоз референсной реализации.

## 18.3 Хранение

| Данные | Где | Формат |
|---|---|---|
| Сеть, планы, отчёты, деньги, takt, компания | локально | сжатый JSON |
| Копия для переноса | файл `.wkrt` | сжатый, с проверкой целостности |
| Расшаренная сеть | сервер, короткая ссылка | 7 дней, потом удаление `[П]` |
| Копии восстановления | локально | «перед загрузкой», «перед перезаписью», «перед файлом», «перед рестартом», «нечитаемое сохранение», «перед ссылкой» `[П]` |

**Уроки из `[П]` (обязательные к реализации):** отдельные кнопки Save/Load; подтверждение перед заменой; автоматические копии; предупреждение о невозможности сохранения с кнопкой «Скачать файл»; защита от перезаписи старой вкладки более новым сохранением; если сохранение не открылось — оно не перезаписывается автосейвом.

## 18.4 Перенос изученного движка

В рабочем репозитории уже реализовано построение матрицы корреспонденций, идентичное движку PlayTakt `[П]`, и подтверждены формулы:

```
Стоимость ребра (обобщённое время), минуты:
we = vn(it) + et·kn + hs(…)·Ko = 405 + 0.25·метры + метры/1.33

Логит-сплит по маршрутам:
Ge = 1 / max(1, cost)

Иерархия режимов: po()
```

Константы: `ae = 1.33`, `Uo = 405`, `ec = 0.25`, `kn = 1`, `Ko = 1`.

**Использование в дизайне:**

- `we` — наша формула обобщённого времени для городов, где нужна **повторяемость с Takt**. Единицы — минуты (405 ≈ 6.75 мин ожидания; 0.25·м — пешеходный множитель; `м/1.33` — деление на «скорость выгоды»; 1.33 совпадает с константой конгестии в `[СБ]`).
- `Ge = 1/max(1, cost)` — **не** классический логит, а обрезанный (ограничение сверху единицей). Дешёвый и устойчивый к выбросам вариант; объясняет, почему Takt-подобные игры не «взрываются» при плохих сетях. Сохраняем как **режим расчёта** и добавляем рядом честный логит из §9.3 для режима «Проверка модели» — так игрок может сравнить две модели.
- Разница между плоской константой движка и 1.39 (`[СБ]`/`[W26]` для ходьбы) — осознанная: движок использует **плоскую** константу, мы используем **дифференцированную**. Это и есть предмет «лаборатории модели» (§14.5).

**Сверка с отраслевой нормой `[Я22]`.** Формула `we` — это наш «режим C», третий сверх двух из §9.7. Её можно интерпретировать так:

| Слагаемое `we` | Интерпретация в терминах `[Я22]` |
|---|---|
| `405` постоянная | фиксированная надбавка за пешеходный подход + ожидание (в минутах); в норме `[Я22]` это **вес 2** против веса 1 у времени в движении |
| `0.25·метры` | пешеходный подход/выход с коэффициентом 0.25 м/мин = **4 м/мин** (быстрее комфортной скорости 5 км/ч = 83 м/мин — то есть это **сильно оптимистично**, движение само компенсирует) |
| `метры/1.33` | обратная величина скорости; `1.33` совпадает с `PERCEIVED_TIME.CONGESTED_DRIVING_MULTIPLIER` в `[СБ]` — то есть движок трактует пробку как «поездку в 1.33 раза длиннее» |

**Проверка согласованности с отраслевой нормой `[Р]`:** чтобы формула `we` была признана пригодной в профиле «Эксперт», она обязана воспроизводить порядок весов 2:1 из §9.7 (ожидание и пересадка дороже движения). Сегодня она даёт вес 1:1 по времени и ~0.25 по пешему пути — **то есть систематически переоценивает движение и недооценивает пешие подходы**. Это фиксируем как известное расхождение и как предмет M0-калибровки: заменяем `we` на шестикомпонентную функцию из §9.7 режима A, сохраняя `we` как «режим C (совместимость с Takt)» для сверки чисел.

**Обязательная проверка:** сумма по матрице = базовый спрос + сумма целей (Берлин: 1 771 979 + 690 889 + 257 868 + 1 469 864 + 129 692 + 950 525 = **5 270 817**). Любой регрессионный прогон обязан это проверять. Второй обязательный тест после перехода на 12–15 слоёв — **совпадение по диапазонам гистограммы распределения спроса по времени** с эталоном `[Я22]`: 34 % / 32 % / 13 % в интервалах 0–20 / 20–40 / 40–60 мин в вечерний пик Перми.
